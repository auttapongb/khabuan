LINE LIFF + Web App for Luxury Car Group Trips

This specification defines product scope, technical architecture, data model, APIs, privacy controls, acceptance criteria, delivery phases, and open decisions. Commercial amounts and dates are intentionally excluded until discovery confirms scale, countries, map provider, and operating model.

1. Executive Summary
MCG Convoy is a private trip coordination experience for luxury-car owner groups. A trip organizer creates an event, sets route and arrival window, and shares a LINE link. Members join, select a vehicle icon, consent to location sharing, and see the convoy on a live map with participant ETAs. The system awards friendly, safety-conscious badges for arrival behavior without encouraging speeding.
Critical product rule  No reward may depend on speed, fastest arrival, aggressive driving, or beating navigation ETA. Scoring is based on safe arrival windows, check-in, consistency, and participation.

1.1 Product outcomes
Reduce organizer effort and repetitive 'where are you?' messages.
Give each participant a clear destination, timeline, convoy status, and privacy state.
Make punctuality and participation enjoyable through opt-in badges and trip summaries.
Keep LINE as the social entry point while providing a more resilient external web experience.

3. Experience and Functional Requirements
3.1 Primary user journey
Organizer creates a trip and defines route, destination, target arrival, grace window, visibility, and optional checkpoints.
System creates an opaque signed invite link. Organizer shares a Flex Message or URL into the desired LINE group.
Member opens LIFF, authenticates with LINE, reviews the trip and privacy terms, then joins and selects a vehicle/icon.
At trip start, member taps Start Sharing. The page requests precise location permission and clearly shows sharing state.
Backend receives samples, calculates route-aware ETA, and streams authorized trip state to active clients.
Member or geofence confirms arrival. The trip closes at an organizer-defined cutoff and awards badges after validation.
Participants receive a trip summary; raw location data expires according to policy.

4. Live Location, ETA and Arrival
4.1 Location behavior
Use the browser Geolocation API after a user gesture and explicit OS/browser permission.
Adaptive sampling target: 3-5 seconds while moving and visible; 10-20 seconds when slow/stationary. Server may throttle; client must stop when trip closes, user stops, consent is revoked, or session expires.
Each sample contains trip/session ID, timestamp, latitude/longitude, accuracy, heading and speed when provided. Do not trust client speed for rewards.
Reject impossible jumps and samples older than the last accepted sample. Preserve the raw value only for short-lived troubleshooting if policy permits; expose normalized position to clients.
Freshness labels: Live <=15 s; Delayed 16-60 s; Stale >60 s. Stale markers are visibly muted and excluded from precise ETA claims.
Map sharing defaults to trip members only. Users may choose approximate location (e.g., 500 m obfuscation) before trip start; exact location is recommended only while active.
4.2 ETA service
ETA is route-aware and traffic-aware when supported by the selected map provider. To control cost, recalculate on meaningful movement, route deviation, destination change, provider TTL, or periodic interval rather than every GPS sample. Cache by participant/destination and display 'calculating' or 'unavailable' instead of inventing an ETA.
Condition

4.3 Arrival determination
Candidate arrival occurs when a good-accuracy position remains within the configured geofence (default 150 m) for a dwell period (default 60 seconds).
Where GPS quality is poor, require manual 'I have arrived' confirmation or organizer confirmation.
Arrival time is the earliest validated candidate, subject to organizer correction with reason and audit log.
Arrival status categories use the organizer's target and grace window; scoring configuration is frozen when the trip opens.
Safety UX  The map must display a persistent 'Do not operate while driving' notice. High-attention actions should be disabled or simplified above a conservative movement threshold, with passenger mode available. This is a risk reduction measure, not proof of who is driving.

6. LINE Integration and Web Fallback
6.1 Channel and account topology
Create a LINE Login channel with LIFF app under the same provider as the MCG LINE Official Account/Messaging API channel so identities remain consistent within the provider boundary.
Enable only required scopes (normally openid and profile); request email only if MCG has a defined operational need.
Validate ID tokens or access tokens on the backend. Do not trust decoded client token content sent as user identity.
Invite the Official Account into each managed group if automated group updates are required; enable group participation in channel settings.
6.2 Group association
A shared URL does not prove which LINE group the user intended. The robust model is an MCG trip membership/invite token in the URL. If the Official Account is present in a group, a webhook can bind that LINE group ID to an MCG club or trip. Otherwise, sharing remains user-driven through LINE's target picker and the system must not claim verified group membership.

6.4 Redirect / continuation design
User taps 'Open full live map' in LIFF.
Backend issues a one-time, short-lived continuation code bound to user, trip, nonce and intended return URI.
LIFF opens the HTTPS web application in an external browser.
Web app performs LINE Login if needed, exchanges the code server-side, and restores trip state.
If identity or nonce differs, deny access and require a fresh invite/login.
Platform limitation  Moving from LIFF to an external browser improves screen space and may improve foreground stability, but it does not create guaranteed background GPS. Mobile operating systems may suspend either browser when the screen locks or the user switches apps.

7. Optional Push-to-Talk (PTT)
PTT should be a separately estimated feature flag and pilot. Implementing it as real-time voice inside a mobile webview requires microphone permission, reliable foreground execution, audio-session handling, low latency, and strict room authorization. Browser/OS behavior can interrupt audio when the screen locks or focus changes.
7.1 Proposed design
Managed WebRTC SFU or equivalent real-time audio service; no custom peer mesh for groups.
Trip-scoped short-lived media tokens issued by backend after membership authorization.
Half-duplex hold-to-talk with server floor control, speaking indicator, mute, block/report and organizer moderation.
Audio is ephemeral and not recorded by default. Recording requires a separate consent, legal and retention design.
Prefer passenger operation; provide oversized single control and audio cues. Do not require map interaction while speaking.

Frontend: TypeScript, React/Next.js or equivalent, LIFF SDK, responsive PWA shell, accessible component system.
Backend: TypeScript/Node.js (NestJS/Fastify) or Kotlin/Java; REST for commands/queries and WebSocket/SSE for live state.

8.3 Event flow
Client obtains location after consent and sends a sequenced sample over authenticated HTTPS/WebSocket.
Gateway validates membership, trip state, timestamp, accuracy, rate and sequence; accepted sample updates ephemeral current position.
Location event updates subscribed trip members with authorization-filtered payload.
ETA worker recalculates only when policy triggers and publishes an ETA update.
Arrival service evaluates geofence/dwell state and creates a candidate event.
Trip closure triggers idempotent scoring and notification jobs; retention jobs remove raw samples.

10. Security, Privacy and Safety
10.1 Threat model priorities
Risk
Required control
Invite forwarding / trip intrusion
Opaque high-entropy tokens, expiry/max use, optional group binding, organizer approval, revocation and rate limits
Location stalking
Trip-scoped authorization, live-only default, consent controls, precise access logs, rapid revoke, no public URLs
Identity spoofing
Server-side LINE token verification, issuer/audience/nonce checks, secure session cookies and CSRF controls
Webhook forgery/replay
Verify LINE signature on raw request body; reject stale/duplicate webhook event IDs
Enumeration
Non-sequential IDs, uniform errors, rate limits and anomaly alerts
Insider misuse
Least privilege, just-in-time support access, audit trail, periodic review and masked admin views
Audio abuse
Trip-bound media tokens, mute/block/report, moderator controls, no default recording

10.2 Privacy requirements
Consent must be specific to live trip location, understandable, recorded by policy version, and revocable at any time.
Default retention proposal: current position until trip + 24 hours; raw samples 7 days; arrival/badge record 24 months; security/audit logs 12 months. Legal/privacy review may shorten or localize these periods.
Provide account data access and deletion workflow; distinguish deletion from records MCG must retain for legitimate security/legal purposes.
Encrypt in transit and at rest; manage secrets in a dedicated secret store; rotate keys and LINE channel secrets.
Do not expose exact home/start locations in post-trip summaries. Apply configurable start/end privacy zones where appropriate.
Complete a privacy impact assessment and country-specific legal review before production, especially for precise location and voice.
10.3 Security engineering
OWASP ASVS-aligned controls, dependency/SAST/secret scanning, penetration test before launch, and tracked remediation.
RBAC with tenant, club and trip scope; deny by default; authorization tests at every object boundary.
Rate and payload limits for auth, invite redemption, location ingestion, WebSocket subscriptions and messaging webhooks.
Backups with tested restore, production access logging, incident runbooks, and vendor risk review for maps/audio.

12.1 Driving-mode interaction rules
Large touch targets; primary screen is glanceable, with no dense chat feed.
No keyboard entry or configuration while movement is detected; defer to passenger mode or stopped state.
Never require members to keep the map visually open solely to prove participation; make location status audible/haptic where browser support allows.
Show explicit controls for Pause sharing and Stop trip sharing at all times.
13. Analytics and Operations
Instrumentation must support product learning and safe operations without turning precise trip location into a secondary analytics dataset.
13.1 Product events
Collect privacy-minimized events: invite_opened, join_completed, vehicle_selected, permission_result, sharing_started/paused/stopped, map_opened, external_browser_opened, eta_available/unavailable, arrival_candidate/confirmed/disputed, badge_awarded, share_initiated, and PTT permission/session metrics. Never put raw coordinates, access tokens, invite tokens, or message contents into analytics.
13.2 Operational dashboards and alerts
Trip API availability/latency/error rate; active trips and live connections.
Location accept/reject rate, end-to-end freshness, stale participant ratio and reconnects.
Routing success/latency/quota/cost; LINE webhook verification failures and push errors.
Database/cache/queue saturation, failed jobs, retention-job lag and backup status.
Security anomalies: invite brute force, excessive location submissions, cross-trip authorization failures and admin access spikes.
13.3 Support tooling
Search by opaque user/trip ID, not precise location; mask personal data by default.
View device/browser capability report, consent state, sharing transitions, sample freshness and provider error codes.
One-click invite revoke, participant remove, trip close and account restriction with reason capture.
Time-limited impersonation is prohibited; use read-only diagnostic views and audited support actions.

15. Acceptance Criteria
AC
Given / when / then
AC-01 Join
Given a valid invite and authenticated LINE account, when the user accepts current terms, then exactly one active participant record is created.
AC-02 Isolation
Given two trips, when a member subscribes to one trip, then no participant, location, ETA or audio metadata from the other trip is returned.
AC-03 Sharing
Given permission granted, when Start Sharing is tapped, then state is visibly active and accepted updates become visible to authorized members within NFR latency.
AC-04 Stop
Given active sharing, when Stop is tapped or trip closes, then new samples are rejected and other clients show sharing stopped/stale within 10 seconds.
AC-05 Permission denied
Given location permission denied, then the app explains how to recover and allows trip participation without pretending the user is live.
AC-06 ETA
Given fresh location and routing availability, then ETA includes timestamp/freshness; on outage it degrades without a false current value.
AC-07 Arrival
Given valid dwell inside geofence, then one arrival candidate is created; repeated samples do not duplicate it.
AC-08 Scoring
Given a frozen rule version and validated arrival, then recalculation produces the same award and reason without duplicate points.
AC-09 Share
Given supported shareTargetPicker capability, then a user can select a LINE recipient and send a trip link without leaking private data in the URL.
AC-10 Fallback
Given the user opens external mode, then a short-lived continuation restores only the authorized trip after LINE authentication.
AC-11 Stale
Given no accepted sample for >60 seconds, then the participant is visibly stale and excluded from live ETA assertions.
AC-12 Retention
Given the retention deadline, then raw location records are deleted or irreversibly aggregated and the deletion job is auditable.
